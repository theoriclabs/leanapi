# Review of M0–M7 at commit 861e93e

Date: 2026-09-22. Scope: the whole repository at `861e93e` (LeanAPI 0.5.0), covering the implementation of [PLAN.md](../../PLAN.md) against [DESIGN.md](../../DESIGN.md) and the claims in [EVIDENCE.md](../../EVIDENCE.md).

Later commits may have fixed some of these findings. Line numbers refer to `861e93e`.

## Summary

The implementation is substantial and works. It builds, all 240 tests pass locally, and the proof audit passes. The persistence core (scoped reads, revision-checked commits, atomic receipts, existence privacy) held up under live concurrent testing.

However, the headline isolation theorem is much weaker than the documentation claims. There is also one data-integrity bug (id wrap-around) and several security bugs in the HTTP toolkit. The post from `intent.md` should not be published on the current `EVIDENCE.md`.

## Critical

### C1. The isolation theorems are near-vacuous

**Files:** `examples/private-games/PrivateGames/Model/Isolation.lean:17-26,170`; `LeanApi/Proofs/Scoped.lean:48,64-68`; `examples/notes/Notes/Shared.lean:40-43,180-183`.

`step_noninterference` assumes `SameViews w₁ w₂ := ∀ p, SameView p w₁ w₂`. That hypothesis quantifies over every player, and every game is visible to its own players. So `SameViews` forces both worlds to contain the same set of games, and the same receipts, sessions, players and `nextGame`. The theorem therefore says nothing about the intended case, where *another user's* games differ while my response stays the same. Adding a game between two other players breaks `SameView` for them, so the hypothesis fails.

Proved counterexample lemmas (Appendix A):

- `games_sameViews_mem : SameViews w₁ w₂ → (g ∈ w₁.games ↔ g ∈ w₂.games)`.
- `notes_sameViews_eq : (∀ u, SameView u w₁ w₂) → w₁ = w₂`. So `Notes.Shared.isolation` reduces to `step r w = step r w`.
- `leaky_ok`: a `ScopedApp` whose `SameView` is equality and whose `load` returns the whole world discharges `Obligations` in three lines. The generic theorem does not constrain `load` to the caller's view.

**What is sound:** `step_noninterference_caller` (`Isolation.lean:180`). If `SameView p w₁ w₂` holds and the request authenticates as `p` in `w₁`, the responses are equal. Other users' data is unconstrained. This is the real isolation result, and `existence_private` rests on it. It covers the response only. The successor-world clause that decision 0009 describes is unproved in the per-caller form. There is no per-caller theorem for notes or for generic `ScopedApp`.

**Affected claims:** EVIDENCE.md claim 1 (line 42) and claim 5 ("a second app gets isolation the same way"); CHANGELOG 0.4.0/0.5.0; README ("decode and core need no proof"); decision 0009.

**Fix:**
- Make the per-caller statement the headline, and add a per-caller successor-view clause.
- Change `ScopedApp.Obligations` to per-caller (`SameView a`), and prove the per-caller theorem generically.
- Add a per-caller theorem for notes.
- Keep the lemmas in Appendix A as regression tests.

### C2. Ids above 2^64 wrap in storage, storing a game the domain forbids

**Files:** `examples/private-games/PrivateGames/Domain/Values.lean:23-27`; `Storage/Schema.lean:101` (`pref`); `Storage/Repo.lean:73` (`gidRef`).

`PlayerId.make` and `GameId.make` reject only 0. Storage converts with `Int64.ofNat`, which wraps around.

Reproduced against the live server:
- Player 1 posted `POST /games {"opponent":18446744073709551617}` and got 201. The self-play check and `validB` passed on the unwrapped number, but the stored row has `x = o = 1`.
- The 201 body and the stored receipt report `"o":18446744073709551617`, which differs from what was stored.
- Afterwards every `GET /games` for player 1 returns 500. One invalid row fails the whole listing (`Repo.lean:221-224`).
- `GET /games/18446744073709551617` returns game 1 (aliasing, still scoped to the caller).

This breaks decision 0006: storage cannot hold a value the API would reject. The write-side check runs on the Lean value, not on the encoded row.

**Fix:** bound ids below 2^63 in the smart constructors, check that encoding round-trips on write, and add huge ids to the differential generator.

## High

### H1. The dummy-hash timing defence is compiled out, so usernames can be enumerated

**File:** `LeanApi/Auth/Tokens.lean:53`, `let _ := verifyPassword pw dummy`.

`verifyPassword` is pure and its result is unused, so the compiler removes it. In `.lake/build/ir/LeanApi/Auth/Tokens.c`, `basicWithPasswords___redArg___lam__0` takes `(lookup, user, pw)` without `dummy`, and calls `Password_verify` only in the known-user branch. A wrong password for a real user costs one scrypt run; an unknown user returns almost immediately.

**Fix:** make the dummy verification effectful and use its result (for example, run it in `IO` and branch on it).

### H2. CORS with any origin plus credentials reflects any Origin

**File:** `LeanApi/Http/Middleware.lean:128-133`.

With `origins := .any, credentials := true`, the request's Origin is echoed with `access-control-allow-credentials: true`. Any site can then read authenticated responses from cookie sessions. The doc comment calls this combination incompatible, but nothing enforces it. Confirmed.

**Fix:** reject the configuration at construction.

### H3. Trusted-proxy handling lets a client spoof its address

**File:** `LeanApi/Http/Middleware.lean:180-185`.

`Forwarded` is preferred over `X-Forwarded-For`. It is also read with `header?`, which returns the first line only. Behind a proxy that only appends `X-Forwarded-For`, a client-sent `Forwarded: for=6.6.6.6` becomes the client address (confirmed), which bypasses per-IP rate limits and allowlists.

**Fix:** make the header source an explicit configuration choice, read all lines, and take the rightmost untrusted hop.

### H4. EVIDENCE.md marks unproved claims as proved

- **Key reuse → 422** is marked Proved (EVIDENCE.md:59), but no theorem about `keyReused` or receipt mismatch exists or is listed in `scripts/audited_theorems.txt`. This violates decision 0011.
- **`keyed_replay`** (`Model/Idempotence.lean:87`) requires a fresh key, a keyed-write plan and a successful commit, and it covers only a replay that is the very next step. EVIDENCE.md:58 and decision 0010 claim every route and input. A replay after any intervening request is unproved.
- **"Resign twice, with or without a key"** (EVIDENCE.md:60): `resign_state_idem` is a core-level lemma for `key = none` only. A second resign under a *different* key is unproved.
- **Existence privacy "separate lemma"** (decision 0009): `hidden_is_constant` is `rfl`, says nothing about refusals, and is not audited.

## Model vs native gaps (under "Assumed 1")

- **Different route tables.** The model routes over 5 `entries`. Native serves `routeTable ++ accountRoutes` inside middleware with a 16 KiB body limit (`App/Service.lean:101-112`). `GET /players` is 404 in the model and 405 natively. `entries` uses `filterMap`, so a template that fails to parse silently drops out of the model (`App/Core.lean:79-80`).
- **Different commit-guard outcomes.** When `commitOk` fails, the model returns 404 (`Model/Step.lean:84`); native returns 412 (`Repo.lean`, `commitDb`). The model re-checks inside the world it loaded from, so the branch is unreachable in sequential runs. The model also has no `Valid` invariant on stored games: natively an invalid row is a 500, while the model serves it.
- **Narrow differential test** (`tests/Tests/Differential.lean`). It never sends:
  - missing auth
  - wrong content type or malformed JSON
  - an invalid Idempotency-Key
  - a missing If-Match
  - non-numeric, zero or huge ids
  - trailing slashes, HEAD or OPTIONS
  - oversized bodies

  It also never compares worlds, and it compares a filtered set of headers. The "63 mismatches" mutation result cannot be reproduced from the repo.
- **Snapshots are not atomic.** Reads are not one snapshot, contrary to decision 0008. `load` uses separate reader connections, and `listVisible` runs `countP` and `fetchFiltered` separately, so `total` and `items` can disagree under concurrent inserts (`App/Service.lean:30-43`, `Repo.lean:219-220`).

## Tests weaker than their names

- `tests/Tests/Games.lean:158` "concurrent same key" accepts 412 as a pass, although 412 should never happen there.
- `tests/Tests/Games.lean:138-146` "exactly one concurrent move wins" uses real concurrency, but cannot distinguish the admission 412 from the commit-time conflict branch. No test hits that branch deterministically.
- `tests/Tests/Games.lean:161-180` "revocation between admission and commit" is sequential: it edits the row via `writeConn` and calls `repo.commit` directly. The app has no revocation feature, so the path is reachable only this way.
- `tests/Tests/Games.lean:75-90` "unauthorized vs missing" compares status and body only. At runtime, headers do match (see below).
- Missing tests: huge ids, commit after timeout, list count/items consistency.

## Low

- `Accept`: `application/json;q=0, */*` still accepts JSON (the more specific range should decide), and `Q=0` in uppercase is treated as q=1 (`Http/Extract.lean:217-239`). Confirmed.
- `{x:nat}`/`{x:int}` accept underscores (`"1_000".toNat? = some 1000`). `{a:int}` and `{b:nat}` do not conflict but both match `5` at equal rank, so declaration order decides, contrary to the router's documented order independence (`Http/Router.lean:44-45`, `Extract.lean:43-44`).
- Cookie `path`/`domain` are not validated. `"/; SameSite=None"` injects attributes. CR and LF are still blocked by the transport (`Http/Response.lean:97-105`).
- Request, trace and span IDs use `IO.rand`, which is predictable. That is fine unless they are ever treated as secrets (`Middleware.lean:59-63`, `Features.lean:148`).

- A 412 is returned to resign or unkeyed writes that lose the compare-and-swap race, although they never sent `If-Match` (`App/Service.lean:23`).
- `.db` and `.corrupt` errors become a generic 500 (good), but the underlying error is never logged (`App/Service.lean:26-27`).

## Verified correct

- **Shared decision code.** The native `operation` (`App/Service.lean:53-66`) calls the shared `authDigest`, `decode` and `core`. The model is not a re-implementation of the decisions.
- **Domain theorems** (`Domain/Proofs.lean`) state what they claim: `decide_allowed`, `decide_transition`, `decide_valid`, `decide_nonparticipant`, `openGame_valid`, `resign_idem`, `resign_resign`, `validB_iff`.
- **`reads_pure`, `unrouted_pure`, `existence_private`** are sound. `read_available` and `gamesApp_step_route` hold but are narrower than their names (core level, and the routed branch respectively).
- **Scoped reads.** The participant filter is pushed into SQL: the LeanDB log shows `pushed: (t0."id" IS ? AND (t0."x" IS ? OR t0."o" IS ?)), residual conjuncts: 0`. Counts use the same predicate. There is no load-then-check path.
- **Compare-and-swap commits.** The replay check, the policy-scoped reload, the revision comparison, the LeanDB compare-and-swap update and the receipt insert all run in one `BEGIN IMMEDIATE` transaction on the single writer (`Repo.lean:124-163`). Live test: 8 concurrent unkeyed moves at rev 0 gave one 200 and seven 412s.
- **Receipts.**
  - Keyed by a unique index on (actor, op, key) and fingerprinted on the canonical input.
  - Written in the same transaction as the change.
  - Not recorded for refused commands.
  - Live tests: 20 concurrent opens with the same key gave 20 × 201, one game and one receipt; 20 concurrent moves with the same key gave 20 × 200 and one move.
  - Replay does not re-check authority, which decision 0010 chose deliberately.
- **Readers.** Opened read-only (`SQLITE_OPEN_READONLY` plus `query_only`). All writes go through the single writer worker.
- **Existence privacy, live.** GET, HEAD, move and resign on another player's game versus a missing id give identical status, headers (including Content-Length and security headers) and body. Only `X-Request-Id` and `Date` differ.
- **JWT:**
  - Only HS256 is accepted; `none` and a missing `alg` are rejected before signature work.
  - `crit` is rejected, and keys under 32 bytes are refused.
  - The HMAC is compared with `CRYPTO_memcmp`.
  - base64url decoding is strict.
  - exp/nbf/iat are checked with leeway using Int arithmetic, `aud` is accepted as a string or an array, and `iss` is checked when configured.
- **Basic and opaque tokens:**
  - Basic: the scheme is case-insensitive, passwords may contain `:`, and base64 decoding is strict.
  - Opaque tokens: 32 bytes from `RAND_bytes`, stored as a SHA-256 digest.
  - scrypt: defaults ln=15, r=8, p=1, with bounded parameters and constant-time hash comparison.
- **leancrypto FFI.** No misuse found: buffer sizes are correct, RNG failure propagates, and empty inputs are handled.
- **HTTP hygiene:**
  - Body limits: an oversized `Content-Length` is refused up front, and chunked bodies are cut off while streaming.
  - No request smuggling: a pipelined request inside an unrouted POST body produced a single 404.
  - `%2F` in a template-matched path, empty segments and `//evil` give 400, so there is no open redirect via trailing-slash handling.
  - Paths are decoded once; header values go through `Header.Value.ofString?`; HEAD bodies are dropped.
  - `recover` and the edge return 500 without internals; client request ids are ignored by default.

## Appendix A: counterexample lemmas

These compile against `861e93e` after `lake build PrivateGames Notes`, with `lake env lean <file>`.

```lean
import PrivateGames.Model.Generic
import Notes.Shared
open PrivateGames PrivateGames.Model LeanApi LeanApi.Proofs

-- Notes: SameViews forces the worlds to be equal.
theorem notes_sameViews_eq {w₁ w₂ : Notes.Shared.World}
    (h : ∀ u : Nat, Notes.Shared.SameView u w₁ w₂) : w₁ = w₂ := by
  have hn : w₁.notes = w₂.notes := by
    funext i
    cases e1 : w₁.notes i with
    | none =>
      cases e2 : w₂.notes i with
      | none => rfl
      | some n =>
        have := (h n.owner).notes i
        simp [Notes.Shared.seen, e1, e2, Notes.Shared.canSee, Option.filter] at this
    | some n =>
      have := (h n.owner).notes i
      cases e2 : w₂.notes i with
      | none => simp [Notes.Shared.seen, e1, e2, Notes.Shared.canSee, Option.filter] at this
      | some m =>
        have h2 := (h m.owner).notes i
        simp [Notes.Shared.seen, e1, e2, Notes.Shared.canSee, Option.filter] at this h2
        rw [this.2]
  cases w₁; cases w₂
  have := (h 0).sessions; have := (h 0).nextId
  simp_all

-- Games: SameViews forces the same set of games.
theorem games_sameViews_mem {w₁ w₂ : World} (h : SameViews w₁ w₂) (g : Game) :
    g ∈ w₁.games ↔ g ∈ w₂.games := by
  have hg := (h g.x).games
  have hv : visible g.x g = true := by simp [visible, Game.isParticipant]
  constructor
  · intro m
    have : g ∈ visibleGames g.x w₁ := List.mem_filter.2 ⟨m, hv⟩
    rw [hg] at this; exact (List.mem_filter.1 this).1
  · intro m
    have : g ∈ visibleGames g.x w₂ := List.mem_filter.2 ⟨m, hv⟩
    rw [← hg] at this; exact (List.mem_filter.1 this).1

-- Leaky generic app: SameView := Eq, load returns the whole world. Obligations hold.
def leaky : ScopedApp where
  World := Nat
  Actor := Nat
  Op := Unit
  Input := Unit
  Need := Unit
  Slice := Nat
  Plan := Res
  SameView := fun _ a b => a = b
  entries := []
  authenticate := fun _ _ => .ok 0
  decode := fun _ _ => .ok ()
  need := fun _ => ()
  load := fun _ w _ => w
  core := fun _ _ s => Res.text (toString s)
  run := fun _ r w => (r, w)

theorem leaky_ok : leaky.Obligations where
  auth_view _ _ _ _ := rfl
  load_view _ _ _ _ h := h
  run_view _ _ _ _ h := ⟨rfl, h⟩
```
