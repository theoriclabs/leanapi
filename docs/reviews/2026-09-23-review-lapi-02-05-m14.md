# Review of LAPI-02…05 on LeanDB M14 (a/b/c), and the blog

Date: 2026-09-23. Scope:
- LeanAPI branch `lapi-02-read-effects` at `69318c2` (LAPI-02, 03, 04, 05; `ec0b23a..69318c2`);
- LeanDB branch `ldb-m14-typed` at `afe4544` (M14a/b/c; `bdd0e4c..afe4544`);
- whether the blog post (`docs/blog/leanapi.md`) compiles and can be published.

## Summary

- **LeanAPI passes everything** on its pin (M14b `d33d067`): the build, 407 tests (including the four-way differential test: model, in-memory typed API, native service, LeanDB-program API), the axiom audit (166 theorems), the README snippets, and the evidence check.
- **LeanAPI was one version behind LeanDB.** M14c (`afe4544`) had not been pushed. With it pushed, LeanAPI builds on M14c after a one-line change (`WithReferrers` now takes `ReferencedBy.Restricting`, M14c's restrict/cascade split), and all of the above passes. The pin is moved to `afe4544` (uncommitted).
- **The blocker is unchanged: `DbState` is empty in proofs** (H1). Every theorem over `DbState` is trivially true, and LAPI-06/07/08 cannot be done honestly until LeanDB M15 gives `DbState` real content.
- **LeanDB's meaning and its SQL also disagree** in ten cases (D1–D10 below, reproduced against SQLite): child-list filters, cascades beyond one level, nullable and child-record foreign keys, `append`, enum ordering, forged `Current` handles, `Nat` above 2^63. So `ExecutesAsMeaning`, the one assumption of the carry-over theorem, is false today. LeanDB's harness exercises none of these cases.
- **LeanAPI's own issues are ticketed:** [LAPI-10](../../tickets/LAPI-10-framework-computed-retry-fingerprints.md) (retry fingerprints), [LAPI-11](../../tickets/LAPI-11-database-endpoints-read-like-the-rest.md) (how database endpoints read), [LAPI-12](../../tickets/LAPI-12-private-games-no-runtime-checks-a-type-can-carry.md) (runtime checks a type can carry). The table at the end lists which repository owns each finding.
- **The blog:** 3 of 12 blocks passed. After aligning the code blocks with what was built, 9 of 13 pass. The four that fail are the theorem statements of LAPI-06/07/08. **It cannot be published yet:** its central claims are not proved.

## High

### H1. `DbState` has no content in proofs; the logic and the compiled code disagree (LeanDB, still at M14c)

`LeanDb/Typed/State.lean` (at `afe4544`): `DbState.load`, `get`, `set` and `source` are `@[implemented_by]`. Their logical bodies ignore the state: `get` is always the empty table, `set` returns the state unchanged. Checked against this repository (a scratch file importing `PrivateGames.DbApi`):

```lean
-- every table of every state is empty
example (st : DbState Games) : (DbState.get (α := GameRow) st).rows = [] := rfl

-- the game a player sees does not depend on the state
example (p : PlayerId) (g : GameId) (st₁ st₂ : DbState Games) :
    Read.denote (DbApi.visibleGame p g) st₁ = Read.denote (DbApi.visibleGame p g) st₂ := by
  simp [DbApi.visibleGame, DbApi.GameRow.visibleTo, DbState.source, DbState.get] <;> rfl

-- the compiled code disagrees with the logic
def t : Table GameRow := { next := 5, rows := [] }
theorem logic : (DbState.get (α := GameRow) (DbState.set (DbState.empty (s := Games)) t)).next = 1 := rfl
theorem runtime : (DbState.get (α := GameRow) (DbState.set (DbState.empty (s := Games)) t)).next = 5 := by native_decide
theorem oops : False := by have := logic.symm.trans runtime; contradiction
-- 'oops' depends on axioms: [propext, Classical.choice, Quot.sound, runtime._native.native_decide.ax_1_1]
```

Consequences:
- The `DbState` laws already proved (`api_step_safe`, `api_inductive`, `getMember_isolated` in `tests/Tests/DbEndpoint.lean`) have the right *form*, but hold for the wrong reason. They are rightly **not** registered as claims in EVIDENCE.md.
- `DbState.WF` (M14c's `checkWF`) is, in the logic, only "the slots are named after the schema's tables": every per-table check runs on an empty table.
- `oops` is caught by the axiom audit (it lists the native axiom). But any use of `native_decide` about a `DbState` is unsound, and LeanDB's `exact_plan` tactic already falls back to `native_decide` (on plan exactness, which does not involve `DbState`, so not exploitable today).

**Fix (LeanDB M15):** give `DbState s` a logical model, e.g. a dependent map `(t : Table) → Table (pack t).ty`, and make the compiled representation provably equal to it, or at least refinement-related, with no `implemented_by` body that differs from the logic. Until then, LAPI-06, 07 and 08 cannot start, and the blog cannot be published.

## Medium

### M1. LeanAPI was pinned one LeanDB version behind (fixed, uncommitted)

LeanAPI's tickets say "done on M14b `d33d067`". LeanDB had M14c on a local branch, unpushed (pushed now). On M14c, `LeanApi/Http/DbProblem.lean:218` failed: `Repr (ReferencedBy s α)` must be `Repr (ReferencedBy.Restricting s α)`, because `DeleteError.restricted` now carries only restricting keys. With that change: build, 407 tests, the axiom audit (166), the README check and the evidence check all pass. `lakefile.toml`/`lake-manifest.json` now pin `afe4544`, and the tickets README records it.

### M2. Receipt fingerprints are hand-written strings

`examples/private-games/PrivateGames/DbApi.lean:83, 126, 138`:

```lean
s!"openGame|{body.val.opponent.n}|{body.val.tc.minutes}"
s!"playMove|{id.val.n}|{rev.val.rev}|{body.val.cell.i}"
s!"resign|{id.val.n}"
```

The fingerprint decides whether a retry replays or is refused (`keyReused`), and it is stored with every receipt. Nothing ties it to the endpoint's inputs:
- add an input to an endpoint and forget it here, and two different requests with the same key replay each other;
- change the format (order, separator, a field's rendering) and every stored receipt stops matching its retries, which then answer 422 instead of replaying (docs/BOUNDARIES.md D10).

**Fix:** derive the fingerprint from the handler's decoded, typed inputs (for example, a canonical encoding of the endpoint's argument tuple, with the endpoint's name and a format version), so that it cannot omit an input and a format change is visible. **Ticket: [LAPI-10](../../tickets/LAPI-10-framework-computed-retry-fingerprints.md).**

### M3. Rows read from LeanDB don't carry their invariant, so a proof needs a runtime check

`DbApi.lean:116-121`: `writeStep` re-checks `GameRow.invariant s.val` in a branch commented "unreachable: LeanDB refuses such a row when it is read". It needs the proof for `GameRow.checkedStep`. LeanDB does refuse such rows on every read (LDB-16), but `Read` returns `Stored GameRow`, which carries no evidence.

**Fix (LeanDB):** return the evidence LeanDB already establishes, e.g. reads of an entity with an invariant give `Stored` rows with `Invariant α r.val`, or a `Checked`-carrying stored row. `writeStep` then needs no runtime branch. With M15's `WF`, this is also what makes "every stored game is valid" a one-line corollary. **LeanDB ask; LeanAPI side: [LAPI-12](../../tickets/LAPI-12-private-games-no-runtime-checks-a-type-can-carry.md) part 2.**

## Low

L1, L2, L3 and L5 are [LAPI-11](../../tickets/LAPI-11-database-endpoints-read-like-the-rest.md); L4 is [LAPI-12](../../tickets/LAPI-12-private-games-no-runtime-checks-a-type-can-carry.md) part 1.

- **L1. The rank-2 `Tx` shows up in every write endpoint.** `Tx s ε ρ := (σ : Type) → Txn σ s ε ρ` (`DbEndpoint.lean:191`) makes each body start with `fun _ =>` (`DbApi.lean:82, 125, 137`), and helpers take `σ` (`keyed`, `writeStep`). The signature reads well; the body doesn't. Making `σ` implicit (`{σ : Type} → Txn σ s ε ρ`) removes the binder. Checked in a scratch file: Lean introduces it, instance resolution goes through, and a `Current` still cannot escape.
- **L2. Two API types and two macros.** `DbApi`/`dbapi!` sit next to `Api`/`api!`, and `dbapi!` repeats `api!`'s checks (`DbEndpoint.lean:558-605`). Since only `DbApi` carries the programs, the carry-over theorem has to be about `DbApi` (LAPI-06 is updated to `DbApi.serve_eq_step`), and `DbApi.step := api.toApi.step` should be added so `gamesApi.step` reads as in the blog. Share the checks between the macros.
- **L3. `LeanApi.Query` (query-string input) and `LeanDb.Query` clash**, so app code writes `LeanDb.Query` and `LeanDb.Query.from` (`DbApi.lean:44-45`). Renaming LeanAPI's input would let the query read as `Query Games [GameRow] …`.
- **L4. `openGame` checks the id range twice** (`DbApi.lean:86`, `:90`), and a caller id ≥ 2^63 would answer `unknownOpponent` (unreachable: `me` comes from a stored token, `pid_lt`). A `PlayerId` that carries its bound, as `PlayerId.make` already checks, would remove both runtime checks.
- **L5. `WithReferrers` renders `reprStr who` into JSON** (`DbProblem.lean:218`), so the wire name is Lean's `Repr` output. It is opt-in, but a stable name from the schema would be better.

## What was checked and is fine

- **`prog_denote`** (`DbEndpoint.lean:263-364`): each endpoint's program denotes exactly its handler's meaning, response and next state, derived over `Path`, pure inputs, `Auth`, `Read` and `Tx`. Once H1 is fixed, this is the per-endpoint half of the carry-over theorem.
- **Authentication inside the snapshot or transaction** (`AuthenticatesDb`): revocation takes effect on the next request, and a write cannot be admitted by a token revoked in the same transaction.
- **Typed failures do their job.** Adding `unique% GameRow.byRev := rev` to the schema breaks the build at `DbApi.lean:93` (the insert) and `:119` (the update) with "Missing cases" (checked in a scratch copy). `Checked GameRow` comes from the domain proofs, with no runtime check (`GameRow.checkedOpen`, `checkedStep`).
- **Problem defaults are blind to payloads** (`DbProblem.lean`), and the wrappers that reveal them are proved not blind.
- **Faults**: 503 plus `retry-after` for locking and full queues, 500 otherwise, logged with the request id, no detail in the body.
- **The receipts deviation (LAPI-05)** is sound: under one writer with `BEGIN IMMEDIATE`, looking up and then inserting is race-free. Claim-first would change answers for keyed requests that write nothing (a repeated resignation), so it needs the reference semantics to change first. The blog now describes the implemented design.
- **EVIDENCE.md** registers no `DbState` theorem as a claim. The new rows (the `GameRow` invariant is `Valid`; written rows are `Checked` from domain proofs) don't depend on `DbState` and are real.

## LeanDB M14: the meaning and the SQL disagree in places

Checked by running each case against SQLite. The repro program is in the review's scratch copy of LeanDB, not in either repository. For each program, compare `denote`, the meaning that proofs are about, with `run`, the SQL: answer, failure, and the tables afterwards. `denote` here is the compiled one, so these disagreements are real even before H1 is fixed.

**This matters for LeanAPI because of LAPI-06.** The carry-over theorem assumes `ExecutesAsMeaning`: LeanDB runs every program as its meaning says. Today that is false in each case below. LeanDB's harness doesn't catch them:
- it uses one fixed schema;
- its random programs only insert, get and look up, on at most 8 rows;
- it has no random update, patch, set, append, delete, `orElse` or `throw`;
- it has no enum ordering, child-list filters, nullable or child-record foreign keys, or two-level cascades.

private-games happens not to trigger any of them: no child-list filters, no enum ordering, no player deletion. But `GameRow.resigned : Option (Ref PlayerRow)` is one of the foreign keys the typed layer doesn't see (L3 below).

**High**
- **D1. Filters on child-list contents.**
  - `r.val.items.any …` / `.all` plan as exact quantifiers over the child table. `run` reads the child rows, but `denote`'s snapshot has only the schema's parent tables (`State.lean:214-219`, `Query.lean:158`).
  - In `denote`, `any` is always false and `all` always true. For bags `[x]` and `[y]`, filtering on "has x" gives `[]`/0 from `denote` and `[hasX]`/1 from `run`.
- **D2. Cascades go one level deep in `denote`.**
  - `deleteCascading` finds the next level with `inferInstance` on an abstract type (`Txn.lean:181`), which picks the empty default instance (`Schema.lean:194`).
  - Org ← Team ← Member, all cascading: deleting the org leaves the member in `denote` (dangling, `checkWF` false); SQLite deletes it.
- **D3. Some foreign keys are enforced by SQLite but invisible to the typed layer.**
  - These are `Option (Ref β)` fields and `Ref`s inside child-list records: `refTarget?` only matches a bare `Id β` (`Schema.lean:553-562`).
  - Inserting with a dangling `some ⟨99⟩`, or deleting a row such a key references, succeeds in `denote` and is a `DbFault` in `run`.
  - The failure is in no error type, and `WF` can't see it.
- **D4. `append`.**
  - The staleness check compares list lengths only (`Txn.lean:141-143`). A same-length change (`[a]` → `[b]`) then passes, and `denote` stores `[a, c]` while SQLite holds `[b, c]`.
  - `append` also checks no unique or foreign key on the parent's columns, and `AppendError` has no `duplicate`/`missingRef`. A clash is `ok` in `denote` and a `DbFault` in `run`.

**Medium**
- **D5. `orderBy` needs `Ord`, not `SqlOrd`** (`Query.lean:80-97`), but a pushed order trusts SQL's.
  - A closed enum is stored as its name, so SQL sorts it alphabetically while `Ord` sorts by constructor.
  - `all`, `first` and `page` answer differently.
- **D6. `Current` can be forged, and programs aren't limited to their schema.**
  - `Current` has a public constructor (`Txn.lean:17`), so `⟨anyStored⟩ : Current σ α` compiles, and `set` on it skips the compare-and-swap.
  - `Read`/`Txn` constructors don't require `IsSchema.Has s α`, so a program can touch entities outside its schema.
- **D7. `Nat` above `Int64.max`.**
  - `set`/`insert` of 2^63 is `ok` in `denote` and a `DbFault` in `run`. `checkWF` compares clamped encodings, so it stays true.
  - `patch` silently stores 2^63−1 in both.
  - Unique-key lookups on such values also disagree (read from the code, not run).

**Low**
- **D8.** `Read.first` after a window with `limit := 0` is `none` in `denote` and `some` in `run` (`Read.lean:103`).
- **D9.** A child-list filter on the left of a `join` is lost in both (`Query.lean:125-128`). They agree, but both are wrong.
- **D10.** A `patch` that breaks an invariant mixing written and unwritten fields is a `DbFault` in `run` and stores the row in `denote` (already a documented deviation).
- The library's `BEq` for `UpdateError`/`AppendError` compares `.stale` by id only (`Write.lean:264, 271`).

**Checked and fine:**
- unique checks run before the write, in declaration order, in both;
- ids come from AUTOINCREMENT, are not reused, and a rollback restores the sequence;
- update's compare-and-swap, with `gone` before `stale`;
- `throw`/`orAbort` restore the start state, and `orElse` keeps earlier writes;
- a page's total and items come from one snapshot;
- joins are pushed as `JOIN … ON`, with the same tiebreaks;
- ordering of strings, options (NULLs first), booleans and integers agrees with SQLite;
- restricted-delete counts agree;
- `Read` has no write constructor, `runRead` refuses a writable connection, and `runTxn` uses `BEGIN IMMEDIATE`.
